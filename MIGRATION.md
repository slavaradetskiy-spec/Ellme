## 1. Что такое ELLME

**ELLME** (`ellme.ru`) — веб-приложение «Дневник питания + аналитика +
работа с нутрициологом», PWA. Открывается в браузере на iPhone/Android
и устанавливается через «Добавить на главный экран» — отдельной нативной
сборки в App Store / Google Play нет. Десктоп тоже работает, но
основное использование — мобильный.

### Кто пользуется

- **Клиенты** (~основная масса) — люди, которые ведут дневник для себя
  или вместе с нутрициологом. Самостоятельно вносят данные о питании,
  сне, движении, самочувствии.
- **Нутрициологи** (~единицы-десятки) — приглашают клиентов через
  invite-код, видят их дневники в read-only, общаются в чате,
  ставят цели на неделю и норму воды.

### Что делает приложение

**Для клиента:**
- Дневник по дням: 3-6 приёмов пищи (фото, описание, время, голод
  до/самочувствие после), вода с подсчётом по нормe, добавки,
  сон (отбой/подъём/качество/заметка), движение (типы активностей
  + длительность), стресс (уровень + практики восстановления —
  дыхание, медитация, йога, массаж), стул, общее самочувствие
  (энергия, настроение, комментарий дня), цель недели.
- Аналитика — графики по 9 метрикам (вода, сон-длительность, сон-
  качество, время отхода ко сну, движение, стресс, энергия, настроение,
  стул) за период 3д/5д/7д/1мес/произвольный.
- Чат с нутрициологом в стиле Telegram: пины, реакции, реплаи,
  форварды, голосовые, фото-вложения.
- PDF-отчёт за период (профиль → дневник по дням с фото → аналитика
  с графиками и нормами) — клиент может скачать или отправить врачу.
- OAuth через Яндекс ID + email/пароль.

**Для нутрициолога:**
- Список клиентов, их дневники в режиме просмотра.
- Лайки на приёмах пищи (одобрение/обратная связь).
- Чат с каждым клиентом.
- Установка нормы воды и цели недели для клиента.
- Свой собственный дневник.
- Скачивание PDF-отчёта по любому из клиентов.

### Бизнес-модель и масштаб

Тарификации и платежей внутри приложения сейчас **нет** — нутрициолог
платит за клиентов сам (или вне платформы), пользователи бесплатно.
Активных юзеров на момент написания — десятки/сотни, не тысячи.
Это важно: масштаб переезда лёгкий по нагрузке (1 Postgres-инстанс
2vCPU/4GB справится), но критичный по данным — это приватная медицинская
информация конкретных людей, теряем — не восстановим.

## 2. Какие данные хранятся

Это не «развлекательное приложение» — это медицинский журнал. Под
192-ФЗ и 152-ФЗ это «персональные данные специальной категории»
(данные о состоянии здоровья). Что конкретно лежит в БД (по схеме
`supabase/schema.sql` + миграции 002-012):

**Профиль (`profiles`)**:
- ФИО, email, телефон, возраст, пол, рост, вес
- «Запрос» (свободное описание целей/жалоб клиента)
- Норма воды (устанавливается нутрициологом)
- Аватар-фото
- Роль: client / doc

**Связи (`doc_clients`)**:
- Кто чей нутрициолог, ник клиента у нутрициолога, статус
  (active/archive)

**Дневник (`diary_days` + `meals`)**:
- День: вода (литры), добавки (свободный текст — часто названия
  лекарств/витаминов), сон (время отхода и пробуждения, качество 1-10,
  заметка), движение (свободный текст + структурированный список),
  стресс (уровень 1-10 + практики), стул, энергия 1-10, настроение 1-5,
  комментарий дня
- Каждый приём пищи: тип (завтрак/обед/...), время, ощущение голода до,
  описание (что ел), самочувствие после, фото
- Цели недели

**Чат (`messages` + миграции 005, 006, 010, 011, 012)**:
- Текстовые сообщения и голосовые между клиентом и нутрициологом
- Файловые вложения (фото, аудио)
- Реакции, пины, реплаи, форварды

**Storage (Supabase Storage, bucket `photos`)**:
- Фото приёмов пищи (`/{userId}/meals/{date}/{mealId}_*.jpg`)
- Аватары
- Чат-вложения (`/{...}/chat/...`)
- Голосовые сообщения

**Auth (`auth.users` в Supabase)**:
- Email + bcrypt-хеш пароля
- Yandex OAuth-связки
- JWT refresh-tokens

**`/api/support`**: форма обратной связи отправляет письмо в email
поддержки через Resend (внешний сервис, США).

> Итого: контактные данные, медицинская история, фото и переписка
> конкретных физлиц. Самые чувствительные пункты — описание добавок
> (часто рецептурные препараты), психологическое состояние (стресс,
> настроение, заметки), переписка с нутрициологом.

## 4. Зачем переезжать (две причины)

### 4.1. Юридическая (152-ФЗ + 242-ФЗ)

**Закон 242-ФЗ** (с 2015 г.) обязывает: «при сборе персональных данных
граждан РФ оператор обязан обеспечить запись, систематизацию,
накопление, хранение, уточнение и извлечение таких данных с
использованием баз данных, **находящихся на территории РФ**».

ELLME сейчас формально нарушает 242-ФЗ: данные граждан РФ хранятся в
Германии (Supabase). Роскомнадзор на медицинский сервис может среагировать
особенно жёстко, потому что речь о специальной категории данных
(здоровье). Штрафы по 13.11 КоАП — до 18 млн ₽ за повторное нарушение
с особой категорией.

Соблюдение требует:
- БД с ПДн физически в РФ (можно дублировать за рубежом, но
  **первичная** запись — в РФ)
- Уведомление РКН о начале обработки ПДн (форма на сайте РКН,
  бесплатно, ~30 дней)
- Политика обработки ПДн на сайте + согласие при регистрации
- Договор с обработчиком (хостером) с прописанными мерами защиты

### 4.2. Техническая (доступность)

`*.supabase.co` периодически блокируется на уровне магистральных
провайдеров и абонентских сетей в РФ (особенно Tele2). Без VPN
клиенты не могут залогиниться. Текущий обходной путь — Nginx-прокся
`api.ellme.ru` на российском VDS (готов в ветке
`claude/supabase-nginx-proxy-Mqn7E`, не активирован) — но это костыль,
который снимается после полноценного переезда в РФ.

## 5. Варианты переезда (три, с обоснованием)

Ключевая дилемма: **managed vs self-hosted** и **один провайдер vs
комбо**. Вот три концепта:

### Вариант A — Минимальный self-host (Timeweb Cloud целиком)

```
[ Timeweb Cloud Apps ] ← Next.js (PaaS, autobuild)
[ Timeweb VDS         ] ← docker-compose с self-hosted Supabase:
                          GoTrue + PostgREST + Realtime + Storage API
                          + Postgres 15 (на той же VDS)
[ Timeweb S3          ] ← фото и вложения
[ Yandex Mail biz     ] ← SMTP (на домене ellme.ru)
```

- **Стоимость**: ~₽800-1500/мес (Apps + VDS 4GB + S3 50GB)
- **Плюсы**:
  - Один провайдер, одна биллинг-панель
  - Самый дешёвый
  - Полный контроль, можно поднять копию на ноуте для разработки
- **Минусы**:
  - **Нет managed Postgres** — бэкапы, ребуты, апгрейды на тебе.
    Если VDS упадёт ночью — приложение лежит до утра.
  - Self-hosted Realtime — самая капризная часть Supabase, нужен
    правильный WAL-репликейшн, может отваливаться под нагрузкой.
  - Apps PaaS у Timeweb молодой, не всегда дружит со сложным
    middleware Next.js — fallback на Docker-режим.
- **Когда выбирать**: на старте, когда юзеров мало и downtime
  допустим. Можно потом переехать в B/C без переписывания кода.

### Вариант B — Гибрид: Timeweb для фронта, Yandex Cloud для данных

```
[ Timeweb Cloud Apps      ] ← Next.js
[ Yandex Cloud Postgres   ] ← managed БД (бэкапы автомат, репликация,
                              сертификат соответствия 152-ФЗ)
[ Timeweb VDS             ] ← docker self-hosted Supabase сервисы
                              (Auth, REST, Realtime, Storage API),
                              подключенные к managed Postgres
[ Yandex Object Storage   ] ← фото и вложения (S3-совместимо,
                              152-ФЗ-сертификат)
[ Yandex Mail biz         ] ← SMTP
```

- **Стоимость**: ~₽3000-5000/мес (Postgres 1vCPU/4GB ~₽2300,
  Apps + VDS ~₽1500, S3 + почта ~₽500)
- **Плюсы**:
  - **Managed Postgres** — точечно решает самую больную часть
    (потеря данных = смерть продукта). Снепшоты, point-in-time
    recovery, мониторинг встроен.
  - Yandex Cloud имеет аттестат соответствия 152-ФЗ — для медицинского
    сервиса это важно, можно ссылаться в политике обработки ПДн.
  - Postgres и S3 у одного провайдера → внутренняя сеть, дешевле трафик
- **Минусы**:
  - Два биллинга, две консоли
  - Yandex Cloud дороже Timeweb в 2-3 раза
  - Self-hosted Realtime всё ещё на тебе
- **Когда выбирать**: когда есть платящие клиенты и downtime реально
  больно. Самый сбалансированный вариант для production.

### Вариант C — Полностью managed на Yandex Cloud

```
[ Yandex Cloud Apps / Serverless ] ← Next.js
[ Yandex Cloud Postgres          ] ← managed БД
[ Yandex Object Storage          ] ← фото и вложения
[ Своя реализация Auth           ] ← либо через Yandex Identity,
                                     либо самописный (NextAuth.js
                                     с Postgres-адаптером)
[ Polling вместо Realtime        ] ← переписать чат и уведомления
                                     на короткий polling (5-10 сек)
                                     или SSE
[ Yandex Mail biz / Postbox      ] ← SMTP
```

- **Стоимость**: ~₽5000-8000/мес
- **Плюсы**:
  - Всё managed, минимальный SRE-оверхед
  - Yandex Cloud — официальный 152-ФЗ-сертификат
  - Масштабируется горизонтально без вмешательства
- **Минусы**:
  - **Нужно переписать Auth** (~2-3 дня) — Supabase GoTrue не работает
    без Postgres-расширений, которых нет в managed Yandex Postgres
  - **Нужно переписать чат** под polling/SSE (~3-5 дней) — нет
    self-hosted Realtime
  - Самый дорогой и медленный по срокам переезда
- **Когда выбирать**: когда уже есть деньги, жирный клиентский
  поток и команда не хочет администрировать VDS.

| Критерий              | A (Timeweb)  | B (Hybrid)    | C (Yandex full) |

## 6. Рекомендация

**Вариант B (гибрид)** — лучший компромисс для текущей стадии:

- Postgres у Yandex Cloud решает главный страх — потерю данных. Это
  единственная нерезервируемая ценность продукта.
- Timeweb для фронта и Auth/Storage сервисов — дешёвый и достаточно
  надёжный для них.
- Аттестат Yandex Cloud по 152-ФЗ — закрывает юридический вопрос.
- Realtime self-hosted — терпимо, чат не критичный для жизни системы
  (если упадёт — новые сообщения не доедут в реалтайме, но при
  обновлении страницы появятся).
- Сроки 7-10 дней реалистичны без героических усилий.

Если бюджет совсем поджимает или это пилот — **A (Timeweb всё)**, с
прицелом потом перевести Postgres в managed.

**C (Yandex full)** имеет смысл когда уже 1000+ платящих клиентов
и пишется новая версия с переписанным auth + чатом — на текущем коде
это лишняя работа.

## 7. Что **дополнительно** нужно завести (помимо самого хостинга)

Эти штуки сейчас «бесплатно» прилетают вместе с Supabase/Vercel —
после переезда придётся настроить руками:

1. **SMTP** для Auth (письма подтверждения, сброс пароля) и
   `/api/support` (форма обратной связи). Резон: рассылать письма с
   российских IP в Gmail/Outlook через сторонние сервисы (Resend,
   SendGrid, Mailgun) часто блокируется из-за IP-репутации.
   - Рекомендация: **smtp.yandex.ru** через Yandex Mail для бизнеса
     (домен `ellme.ru`), либо **mail.ru для бизнеса**. Оба — полноценные
     SPF/DKIM/DMARC, RU-IP, бесплатно до ~1000 писем/день.
2. **S3-совместимое хранилище** под фото/чат-вложения. Альтернативы:
   - **Timeweb S3** (≈₽0.6/ГБ месяц, есть public ACL и CORS)
   - **Yandex Object Storage** (≈₽1.4/ГБ месяц, проверенная репутация)
   - Selectel (если уже есть аккаунт)
3. **Бэкапы**:
   - Postgres: managed-сервис делает автоматические снепшоты, но
     дополнительно — `pg_dump` крон-таска раз в сутки в S3 с retention
     14 дней. Без этого — переезд → отказ managed → потеря данных.
   - Storage: S3 versioning + lifecycle rule (90 дней).
4. **Мониторинг**:
   - Uptime: **Uptime Kuma** на отдельной мини-VDS (₽150/мес, открытый код).
   - Ошибки фронта: **GlitchTip** или **Sentry self-hosted** (на Docker).
   - Логи: достаточно `journalctl` + `logrotate` на VDS, без ELK.
5. **TLS**: Let's Encrypt + certbot для всех поддоменов
   (`ellme.ru`, `api.ellme.ru`, `db.ellme.ru` или как назовём auth-сервер).
6. **DNS**: оставляем у текущего регистратора, но **переключаемся на
   Cloudflare** для оркестрации (бесплатно). Cloudflare блокируется
   ICANN-аккаунтами в РФ редко, но если страшно — переехать к Reg.ru.
7. **Push-уведомления** (если планируется): Web Push нативно через сам
   Next.js + service worker, но ключи VAPID нужно сгенерировать заранее.

## 8. План по этапам (~5–7 дней для варианта A, 7–10 для B)

### Этап 0. Подготовка (0.5 дня)
- Регистрируем аккаунт Timeweb Cloud, привязываем платёжку.
- Заводим Yandex Mail для бизнеса на домене `ellme.ru`,
  настраиваем SPF/DKIM/DMARC.
- Создаём S3-bucket в Timeweb (public-read для папки `meals/`,
  privacy для `chat/`). Прописываем CORS для `https://ellme.ru`.

### Этап 1. Backend (2 дня)
- Поднимаем VDS на Timeweb (Ubuntu 22, 2vCPU/4GB достаточно для старта).
- Поднимаем Managed PostgreSQL (Timeweb или Yandex Cloud).
- Self-host Supabase через docker-compose (репозиторий
  `supabase/supabase`, `docker/docker-compose.yml`):
  - Studio, Kong (gateway), Auth (GoTrue), REST (PostgREST),
    Realtime, Storage API, ImgProxy, Edge Functions (если понадобятся).
  - **Подключаем к managed Postgres**, не используем встроенный.
  - SMTP в `.env` GoTrue: `smtp.yandex.ru:465`, наш аккаунт.
  - Storage backend: S3 (см. этап 0), не локальный диск.
- TLS: certbot для `auth.ellme.ru` (или как назовём API-домен).

### Этап 2. Миграция данных (0.5 дня)
- `pg_dump --schema-only` старого Supabase → ревью миграций.
- `pg_dump --data-only` старого → restore в новый. Если есть `auth.users`
  — миграция через GoTrue `/admin/users`-API (хеши паролей сохраняются,
  GoTrue использует bcrypt совместимо).
- Перенос Storage: `rclone` или `aws s3 sync` из supabase storage
  через REST в новый S3-bucket.
- Прописать в `profiles.photo_url` и `meals.photo_url` новые URL
  (regex-replace в SQL по старому Supabase-домену).

### Этап 3. Frontend (1 день)

### Этап 4. Cutover (0.5 дня)

- Меняем DNS A-запись `ellme.ru` на Timeweb-инстанс. TTL=300 заранее.
- Отключаем maintenance, делаем дымовой тест: регистрация, логин,
  загрузка фото, чат, аналитика, PDF-экспорт.

## 9. Риски и митигация

| Риск                                    | Митигация                                           |
| --------------------------------------- | --------------------------------------------------- |
| Письма от Yandex SMTP падают в спам Gmail | DKIM + DMARC обязательно, прогрев домена 1-2 недели до миграции. Подождать с продакшеном. |
| Realtime WS медленнее чем у Supabase    | На Timeweb VDS низкий пинг для РФ, должно быть лучше. Тест на 100+ конкуррентных WS до cutover. |
| OAuth Yandex callback ломается из-за смены `redirect_uri` | До cutover в Yandex OAuth-консоли добавить НОВЫЙ redirect, оставив старый. |
| Хеши паролей не переносятся             | GoTrue использует bcrypt — совместимо. Если нет — `/admin/generate-link?type=recovery` для всех юзеров и форс-сброс. |
| Managed Postgres подвисает на крупный pg_restore | Делаем pg_restore в off-peak, ставим `--jobs=4`, разбиваем на схемы. |
| Прокся `api.ellme.ru` (текущая) станет лишней | Снять Nginx-конфиг и DNS после успешного cutover. Или оставить как «классический» api-роутер для будущего. |

## 10. Открытые решения (нужно слово от владельца)

- [ ] **Хостинг Next.js**: Timeweb Cloud Apps (PaaS) или Docker на VDS?
  PaaS быстрее, но менее гибкий с middleware и cron.
- [ ] **Postgres**: Timeweb Managed или Yandex Cloud Managed?
  Yandex дороже, но надёжнее (репликация, восстановление).
- [ ] **S3**: Timeweb S3 или Yandex Object Storage? Если Postgres у
  Yandex — логично и S3 там, для меньшей сетевой латентности.
- [ ] **Email**: Yandex Mail для бизнеса или Mail.ru? Yandex привычнее
  для разработки, Mail.ru исторически выше дофигачит дофинеабельность RU.
- [ ] **Цель миграции**: только обход блокировок Tele2 или ещё и
  152-ФЗ (хранение ПДн в РФ)? Если 152-ФЗ — нужен договор с
  оператором ПДн (Yandex Cloud имеет нужный сертификат, Timeweb тоже).
- [ ] **Окно cutover**: предупреждать клиентов за неделю или сделать
  ночью без анонса? Сейчас юзеров мало, ночь без шума ок.
